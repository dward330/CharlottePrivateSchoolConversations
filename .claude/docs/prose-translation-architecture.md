# Research-prose translation — architecture

**Status:** proposed, not built. Written 2026-07-27.
**Scope:** how *any* language translates the research prose inside the cards.
Language-independent by design — the per-language rollout lives in its own doc
(`prose-translation-<lang>.md`; Spanish is `prose-translation-es.md`).

The UI chrome is already translatable (PRs #40–#43) via `src/locales/<lang>.json`.
This document covers the other layer: the research prose, which is why a Spanish
reader today sees Spanish headings above English paragraphs.

---

## 1. What the repo actually does

Two findings here were verified against the code, not assumed. Both change the
approach earlier notes had been working from.

### 1a. There are TWO prose bodies, with opposite maintenance properties

| Layer | Words | Authored by | Regenerated by ingest? |
|---|---|---|---|
| `src/data/**/<school>.ts` (structured cards) | **~106k** | hand, per redesign PR | **No** |
| `src/content/<topic>/<school>.json` | **~321k** | `build_site_content.py` | **Yes, every pass** |

Earlier notes treated the prose as one ~165k-word body regenerated by the pipeline.
That is not what the repo does. The structured card layer under `src/data/` is
**hand-authored and never touched by the ingest pipeline** — confirmed three ways:

- `build_docs.py` / `build_site_content.py` write only `.claude/docs/`,
  `src/data/schools.json`, and `src/content/` (see the data-flow diagram in the
  ingest skill: *"pipeline ends here — everything below is HAND-MAINTAINED"*).
- No script references `sportsPrograms|artsPrograms|collegeSupportPrograms`.
- Git history: those files change only in redesign PRs (#32–#37), never in ingest passes.

**Consequence:** the desync fear that motivated "locale-keyed data files, never
translation JSON" applies to `src/content/`, **not** to `src/data/`. The `src/data/`
layer is as stable as source code. This is the single most important fact here.

### 1b. Most of the generated prose is no longer rendered

The redesign substituted structured cards for ingested prose, topic by topic.
`SchoolDetail.tsx` shows the branching. Current state:

| Topic | Generated prose | Rendered today? |
|---|---|---|
| sports | 66k | **No** — fully replaced by `SPORTS_CARDS` |
| the-arts | 43k | **No** — fully replaced |
| college-support | 78k | **No** — fully replaced |

| course-offerings | 27k | **No** — replaced by `courseOfferings()` |
| student-clubs | 35k | **Partly** — only `academic-clubs` + `catalog` groups survive |
| financial-aid-tuition | 39k | **Yes** — the only topic still prose-first |

So the user-visible surface is **not 321k words**. It is roughly ~106k of `src/data/`
card content (minus non-translatables), ~39k of financial-aid prose, and ~5k of
surviving Student Clubs prose.

Much of the `src/data/` total is **not translatable text at all**: `url` (152),
`name` of sports/schools (228), `value` figures, `year`, `result`, `levels`,
`startFrac`/`endFrac`, hex `shade`. The genuinely translatable fields are `headline`
(141), `subhead` (141), `text` (463), `detail` (142), `label` (511), `note` (93),
`footnote` (18), `caption`, `desc`, `hint`, `verdict`.

**Measured translatable surface: 53,397 words per language** across 3,045 field sites
(2,637 distinct strings) — not 165k and not 321k.

## 2. The mechanism

### Sidecar locale files at the data layer, keyed by field path

```
src/data/sportsPrograms/cannon.ts        ← English, source of truth (unchanged)
src/data/sportsPrograms/cannon.es.ts     ← Spanish overlay, same shape, partial
src/data/sportsPrograms/cannon.fr.ts     ← French overlay, later, independent
```

Resolved by one generic helper — **not** per-topic or per-language plumbing:

```ts
// src/lib/localizeData.ts
export function localized<T>(en: T, overlay: DeepPartial<T> | undefined): T
```

A deep merge where the overlay wins field-by-field and **any missing field falls back
to English automatically**. Partial overlays are a first-class state, exactly as
`parseMissingKeyHandler` already does for UI chrome.

**Requirement — identity preservation.** When there is no overlay for the active
locale, `localized()` MUST return the *exact English object reference*, not a merged
copy. The call sites in `SchoolDetail.tsx` carry deliberate truthiness logic (see the
comments warning that "an entry that is present but empty is still truthy, and would
otherwise suppress the prose and leave the whole section blank"), and several derive
render decisions from object presence. Returning a fresh object identity per render
risks re-render churn or a silently dropped section — and would hit **English**
readers. This is a hard requirement, not an optimization.

Wire-up is one line per topic loader, inside the existing accessor, so components
never learn that locales exist:

```ts
export function sportsProgram(slug: string, lang: string): SportsProgram | undefined {
  const en = PROGRAMS[slug]
  return en && localized(en, OVERLAYS[lang]?.[slug])
}
```

Overlays load through `import.meta.glob` with the lazy-chunk pattern
`src/lib/i18n.ts` already uses for catalogs, so a reader of one language never
downloads another's bytes.

**Everything is keyed by `<lang>`, never hardcoded to a specific locale** — overlay
glob (`*.<lang>.ts`), translation-memory keys, extraction output paths. Spanish is
the first consumer, not a special case. This costs nothing now and is tedious to
retrofit.

### Why this over the alternatives

**Why not translation JSON (`es.json`)?** Correct for chrome, wrong here. It would
put ~50k words of factual research into a file whose keys are invented rather than
structural, and it breaks the property that matters most: a reviewer cannot check
*"Cannon's 1c pipeline paragraph"* against its English original when both are
flattened into a 3,000-key blob. Sidecars keep the translation physically adjacent to
the English it translates.

**Why not translate in place, or keep a full copy per language?** A full copy doubles
the bytes a redesign PR must keep in step and gives no signal about *which* fields
drifted. A partial overlay is self-documenting: what's in the file is translated,
what's absent falls back.

**Why not runtime machine translation?** It re-translates on every page view, cannot
be reviewed before shipping, and would silently paraphrase the deliberate hedges
("school-reported, no methodology published") that make this research honest.

### The staleness problem, and what solves it

This is the part that must be right, because content *will* keep changing.

An overlay that silently keeps serving a translation of a paragraph whose English has
since been rewritten is **worse than no translation** — it presents outdated facts
about tuition and admissions with full authority, and the reader cannot detect it
because they do not read English.

**Mechanism: content-hash stamping.** Each overlay field carries a hash of the English
string it was translated from:

```ts
export const cannon: Overlay<SportsProgram> = {
  offered: {
    headline: { t: '35 equipos en 13 deportes…', of: 'a3f21c' },
  },
}
```

- `scripts/check_translations.mjs` (new, modeled on `check_metrics.mjs`) recomputes
  each English field's hash and reports every overlay entry whose `of` no longer
  matches. **Advisory and exits non-zero — not CI-blocking.** A blocking check on a
  layer that drifts by design would get routinely bypassed, at which point it stops
  protecting anything. Same posture as `check_metrics.mjs`.
- At **runtime**, a stale entry falls back to English rather than rendering.

Staleness degrades to an untranslated paragraph — **never to a wrong one.** This is
the non-negotiable safety property, and it is what makes the layer safe to leave
partially maintained indefinitely.

This inverts the maintenance burden correctly: changing English prose never *breaks*
the site. It quietly reverts that one field to English and raises a checklist item.

## 3. Token efficiency

Translating ~50k words by pasting files into context and re-emitting them is the
expensive path: every `url`, hex code and figure gets read and rewritten, and
whole-file rewrites risk corrupting non-text fields.

**Extract → translate → reinject.** Three scripted steps, one model step:

1. **Extract** (`scripts/i18n-extract.mjs`): walk each topic's English module, pull
   only whitelisted translatable field paths, emit a flat work file:
   ```json
   { "offered.headline": "35 teams across 13 sports…", "offered.stats.0.label": "distinct sports" }
   ```
   Non-translatable keys never enter model context at all.
2. **Translate**: the model sees only strings needing translation, batched per school
   × topic. No code, no URLs, no figures, no structural re-emission.
3. **Reinject** (`scripts/i18n-build-overlay.mjs`): writes the `.<lang>.ts` overlay
   with hashes computed mechanically. The model never hand-writes an overlay file, so
   it cannot typo a hash or drop a field.

A translation-memory map (`en string → {lang: translated}`, exact match) is applied
before the model is called, so each distinct string is translated **once** and reused
at every site it occurs.

> **Measured 2026-07-27 — the dedupe saving is 2%, not "well over half".** The
> earlier estimate was wrong. Repetition is real but concentrated in short status
> codes (`STATE` ×44, `NONE` ×51, `RUNNER-UP` ×15), which carry almost no words;
> only 31 of 520 Sports strings recur at all. The prose that dominates the word
> count — `text` (15.8k words), `detail`, `headline`, `subhead` — is per-school
> research and is **almost entirely unique by nature**. Keep the TM (it is nearly
> free and prevents inconsistent renderings of the same label), but do not budget
> against it.

**The real token saving is the extraction itself, and it is large.** The model sees
only prose strings: no URLs, hex codes, layout numbers, proper nouns, or structural
re-emission. Against the ~430k words of mixed code and data in the raw files, the
translatable surface is ~53k words — roughly an 8× reduction, and it comes from the
whitelist, not the dedupe.

## 4. Per-language work that this doc does NOT cover

The mechanism above is language-independent. What genuinely varies is small, and
mostly script/layout rather than architecture:

- **RTL locales (Arabic, Farsi)** — the one real unknown. When their prose lands, the
  `:root[dir='rtl'][data-prose='en'] main { direction: ltr }` pin retires for that
  locale and the prose renders RTL for the first time. Nobody has seen that state.
  Deserves its own investigation — but it is an *RTL* question answered once for both
  locales, not a per-language one.
- **Non-Latin scripts** (Bengali, Hindi, Telugu) — font loading is already wired in
  `syncFont()`, but line-height and heading metrics in a design built for Barlow are
  untested at paragraph length.
- **Text expansion** — Spanish runs ~20% longer than English, German more. Fixed-width
  stat tiles may need checking; what's learned transfers to later languages.

Adding a second language should cost a short rollout doc, **not** a repeat of the
research in §1.

## 5. Rollout rules that apply to every language

- **One topic at a time, never one bulk pass.** Not for review reasons — a topic is
  the unit that fits a PR, keeps a diff readable, and lets the machinery be corrected
  before it is applied five more times.
- **Order stages cheapest and lowest-stakes first**, so the machinery is proven before
  it touches admissions outcomes and tuition. Financial Aid last, always.
- **Do not add a locale to `PROSE_TRANSLATED` until its rollout is complete.** That
  list drives `data-prose` on `<html>` and the RTL LTR-pin CSS rule; it asserts "the
  prose is translated", and a partial state must not claim that.
- **How and when a language is reviewed is a per-language decision**, recorded in that
  language's rollout doc rather than mandated here. Spanish reviews once at the end
  (owner's decision, 2026-07-27). Note what is being traded: the prose carries
  deliberate hedges that a loose translation destroys, and a mistranslation is
  invisible to a reader who does not read English, so a systematic error surfaces
  later rather than sooner. Keeping per-stage translation notes in
  `src/data/overlays/NOTES.md` is the cheap mitigation.

## 5a. Three layers, not two — card titles are chrome

Strings that live in **module constants in the topic loaders** (`SPORTS_CARDS`,
`ARTS_CARDS`, `CLUBS_CARDS`, `COLLEGE_SUPPORT_CARDS`, `AFTER_SCHOOL_CARDS`) are
in neither place the two i18n passes looked: not in a component, and not in the
per-school entry objects the prose extractor walks. All 25 card titles shipped
English inside otherwise-Spanish pages before this was caught.

**They are chrome.** By CLAUDE.md's uniform test — byte-identical for every
school, drawn from a fixed lookup — they belong in `src/locales/*.json`, under
`cards.<topic>.<key>`. Resolved by `cardTitle()` in `src/lib/labels.ts`.

**Per-school `TITLE_OVERRIDES` are the exception, and they stay in the locale
files anyway.** An override (`'The Early Childhood–12 Arts Ladder'` for Davidson
Day) varies per school, so by the same test it is a research finding rather than
chrome. But it is *defined in the same module constant*, which the prose
extractor cannot reach — so an overlay could not carry it. They get a
**school-scoped key** instead:

```
cards.the-arts.ladder                      shared — five schools
cards.the-arts.ladder@davidson-day         this school's own wording
```

A school without a translated override falls back to its own English title,
never to another school's. There are seven of these today.

**Rule for future topics:** when a redesign adds a `*_CARDS` constant, its
titles are locale keys from the start. `scripts/check_card_titles.mjs` fails if
any card title has no `cards.*` key.

## 5b. As built (Stage 1, 2026-07-27)

The mechanism above is implemented. Three details that were decided in the build
rather than in the plan:

**Two files per topic per language, not one.**

```
src/data/overlays/work/student-clubs.es.json   English + Spanish — the REVIEWABLE artifact
src/data/overlays/student-clubs.es.json        Spanish only — what the app SHIPS
```

`i18n_build_overlay.mjs` compiles the second from the first, stripping the English
`text` and dropping untranslated entries. The runtime never needs the English — it
re-derives the hash from the live `src/data/**` — so shipping it would send the
corpus to the browser twice. Measured: **35% smaller**, 80,580 → 49,479 bytes for
Student Clubs. The work file stays committed, because a reviewer cannot check a
translation without the original beside it.

**The stamp is FNV-1a, not sha256.** The runtime must compute the identical hash
in the browser, where `node:crypto` does not exist. It lives in its own module
(`scripts/i18n_stamp.mjs`) so importing it has no side effects, and
`scripts/check_hash_parity.mjs` asserts the build-time and runtime implementations
agree — including on non-ASCII, since this prose is full of curly quotes and
accents. **If those two ever diverge, every entry reads as stale and the locale
silently renders English with no error.** That check is the guard against a
total, invisible loss of translation.

**Overlays load behind the existing `ready` gate.** `SchoolDetail` already
withholds render until its notes resolve; the overlay fetch joins that same
`Promise.all`. Resolving it later would paint English research for a frame and
then swap it, which reads as a glitch rather than as a language.

## 6. Stage 0 — the only thing to build before any language commits

**Scope: measurement and checking tooling only.**

- `scripts/i18n-extract.mjs` — the field whitelist and extraction walk
- `scripts/check_translations.mjs` — hash drift reporting
- The translation-memory dedupe pass

**Deliberately NOT in Stage 0: the `localized()` helper and the accessor rewiring.**
Those change `sportsProgram(slug)` → `sportsProgram(slug, lang)` across six topic
loaders and their call sites in the render path — English-facing risk taken on behalf
of a language nobody is reading yet. That work belongs to the first *content* stage,
when an overlay actually exists to resolve. Until then the render path is untouched.

Stage 0 has **no user-visible effect in any language** and is safe to land alone. Its
payoff is immediate and language-independent: it replaces the extrapolated ~45–55k
estimate in §1 with a measured number, which is what tells you how much reviewer time
you are actually asking for.
