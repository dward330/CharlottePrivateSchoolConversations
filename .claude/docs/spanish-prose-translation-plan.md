# Spanish research-prose translation — architecture & execution plan

**Status:** proposed, not started. Written 2026-07-27.
**Goal:** translate the words *inside the cards* into Spanish, in a way that survives
continuous content change and costs the least tokens per unit of translated text.

The UI chrome is already Spanish (PRs #40–#43). This plan covers only the research
prose, which is why a Spanish reader today sees Spanish headings above English
paragraphs.

---

## 1. What the research actually found

Two findings materially change the approach recorded in earlier notes. Both were
verified against the code, not assumed.

### 1a. There are TWO prose bodies, with opposite maintenance properties

| Layer | Words | Authored by | Regenerated by ingest? |
|---|---|---|---|
| `src/data/**/<school>.ts` (structured cards) | **~106k** | hand, per redesign PR | **No** |
| `src/content/<topic>/<school>.json` | **~321k** | `build_site_content.py` | **Yes, every pass** |

Earlier notes treated the prose as one ~165k-word body regenerated by the pipeline.
That is not what the repo does. The structured card layer under `src/data/` is
**hand-authored and never touched by the ingest pipeline** — confirmed three ways:

- `build_docs.py` / `build_site_content.py` write only `.claude/docs/`,
  `src/data/schools.json`, and `src/content/` (see the data-flow diagram in the
  ingest skill: *"pipeline ends here — everything below is HAND-MAINTAINED"*).
- No script references `sportsPrograms|artsPrograms|collegeSupportPrograms`.
- Git history: those files change only in redesign PRs (#32–#37), never in ingest passes.

**Consequence:** the desync fear that motivated "locale-keyed data files, never
translation JSON" applies to `src/content/`, **not** to `src/data/`. The `src/data/`
layer is as stable as source code. This is the single most important fact in the plan.

### 1b. Most of the generated prose is no longer rendered

The redesign substituted structured cards for ingested prose, topic by topic.
`SchoolDetail.tsx` shows the branching. Current state:

| Topic | Generated prose | Rendered today? |
|---|---|---|
| sports | 66k | **No** — fully replaced by `SPORTS_CARDS` |
| the-arts | 43k | **No** — fully replaced |
| college-support | 78k | **No** — fully replaced |
| after-school | 26k | **No** — fully replaced |
| course-offerings | 27k | **No** — replaced by `courseOfferings()` |
| student-clubs | 35k | **Partly** — only `academic-clubs` + `catalog` groups survive |
| financial-aid-tuition | 39k | **Yes** — the only topic still prose-first |

So the user-visible surface is **not 321k words**. It is roughly:

- ~106k words of hand-authored `src/data/` card content, minus non-translatables
- ~39k words of financial-aid prose
- ~5k words of surviving Student Clubs prose

And of the `src/data/` total, a large share is **not translatable text at all**:
`url` (152), `name` of sports/schools (228), `value` figures, `year`, `result`,
`levels`, `startFrac`/`endFrac`, hex `shade`. The genuinely translatable fields are
`headline` (141), `subhead` (141), `text` (463), `detail` (142), `label` (511),
`note` (93), `footnote` (18), `caption`, `desc`, `hint`, `verdict`.

**Working estimate of real translatable surface: ~45–55k words**, not 165k and not
321k. That is a ~3–6× reduction in scope versus the earlier assumption, and it is
the reason this is now tractable.

## 2. Architecture — the recommendation

### Chosen: sidecar locale files at the data layer, keyed by field path

```
src/data/sportsPrograms/cannon.ts        ← English, source of truth (unchanged)
src/data/sportsPrograms/cannon.es.ts     ← Spanish overlay, same shape, partial
```

Resolved by a single generic helper, not per-topic plumbing:

```ts
// src/lib/localizeData.ts
export function localized<T>(en: T, overlay: DeepPartial<T> | undefined): T
```

A deep merge where the overlay wins field-by-field and **any missing field falls
back to English automatically**. Partial overlays are a first-class state, exactly
as `parseMissingKeyHandler` already does for UI chrome.

Wire-up is one line per topic loader, inside the existing `sportsProgram(slug)`
accessor — the components never learn that locales exist:

```ts
export function sportsProgram(slug: string, lang: string): SportsProgram | undefined {
  const en = PROGRAMS[slug]
  return en && localized(en, ES_PROGRAMS[lang]?.[slug])
}
```

Overlays load through `import.meta.glob` with the same lazy-chunk pattern
`src/lib/i18n.ts` already uses for catalogs, so English readers never download
Spanish bytes.

### Why this over the alternatives

**Why not translation JSON (`es.json`)?** Correct for chrome, wrong here. It would
put 50k words of factual research into a file whose keys are invented rather than
structural, and it breaks the reviewability property that matters most: a reviewer
cannot check *"Cannon's 1c pipeline paragraph"* against its English original when
both are flattened into a 3,000-key JSON blob. Sidecars keep the Spanish physically
adjacent to the English it translates.

**Why not translate in place / a second full copy of each file?** A full copy doubles
the bytes a redesign PR must keep in step and gives no signal about *which* fields
drifted. A partial overlay is self-documenting: what's in the file is translated,
what's absent falls back.

**Why not runtime machine translation?** It re-translates on every page view, cannot
be reviewed before shipping, and would silently paraphrase the deliberate hedges
("school-reported, no methodology published") that make this research honest.

### The staleness problem, and the mechanism that solves it

This is the part that must be right, because content *will* keep changing.

An overlay that silently keeps serving a translation of a paragraph whose English
has since been rewritten is **worse than no translation** — it presents outdated
facts about tuition and admissions with full authority, and the user cannot detect
it because they do not read Spanish.

**Mechanism: content-hash stamping.** Each overlay file carries a hash of the English
source string it was translated from:

```ts
export const cannon: EsOverlay<SportsProgram> = {
  offered: {
    headline: { es: '35 equipos en 13 deportes…', of: 'a3f21c' },
  },
}
```

- `scripts/check_translations.mjs` (new, modeled on the existing `check_metrics.mjs`)
  recomputes each English field's hash and reports every overlay entry whose `of`
  no longer matches. Exits non-zero. Wired into the ingest checklist and CI.
- At **runtime**, a stale entry falls back to English rather than rendering. Staleness
  degrades to an untranslated paragraph — never to a wrong one. This is the
  non-negotiable safety property and it is what makes the whole layer safe to leave
  partially maintained.

This inverts the maintenance burden correctly: changing English prose never *breaks*
the site, it just quietly reverts that one field to English and raises a checklist
item.

## 3. Token efficiency — how the work is actually done

Translating 50k words by pasting files into context and re-emitting them is the
expensive path: every `url`, hex code, and figure would be read and re-written, and
whole-file rewrites risk corrupting the non-text fields.

**Extract → translate → reinject.** Three scripted steps, one model step:

1. **Extract** (`scripts/i18n-extract.mjs`): walk each topic's English module with
   the TypeScript AST (or a JSON round-trip of the imported object), pull only the
   whitelisted translatable field paths, and emit a flat work file:
   ```json
   { "offered.headline": "35 teams across 13 sports…", "offered.stats.0.label": "distinct sports" }
   ```
   Non-translatable keys never enter the model's context at all.
2. **Translate**: the model sees only strings needing Spanish, batched per school ×
   topic. No code, no URLs, no figures, no re-emission of structure.
3. **Reinject** (`scripts/i18n-build-overlay.mjs`): writes the `.es.ts` overlay with
   hashes computed mechanically. The model never hand-writes an overlay file, so it
   cannot typo a hash or drop a field.

Deduplication before step 2 is where the real savings are. `label` alone is 511
occurrences across a small vocabulary — `"distinct sports"`, `"teams across V · JV ·
MS"`, `"of grades 5–12 participate"` recur across all six schools. A
translation-memory map (`en string → es string`, exact match) is applied before the
model is called, so each distinct string is translated **once** and reused across all
six schools. Expect this to cut the label/caption surface by well over half.

Net: the model translates ~45–55k words of genuine prose *once*, with essentially no
structural tokens, instead of re-emitting ~430k words of mixed code and data.

## 4. Staging — the review gate stays

Per the standing decision, this ships **one topic at a time with a native-speaker
review between stages**, never as one bulk pass. The reason is unchanged and still
sound: this is factual research families use for five-figure decisions, the prose
carries deliberate hedges, and a mistranslation is invisible to a user who does not
read Spanish.

Recommended order — cheapest and lowest-risk first, so the machinery is proven before
it touches the highest-stakes content:

| Stage | Scope | Why here |
|---|---|---|
| 0 | Build `localized()`, extract/reinject scripts, `check_translations.mjs`; no prose | Land and review the machinery alone |
| 1 | **The Arts** (~8k translatable) | Lowest stakes; proves the pipeline end-to-end |
| 2 | **Sports** (~10k) | High volume, heavy label reuse — validates the TM dedup |
| 3 | **Student Clubs** (~5k + surviving prose) | Small; exercises the mixed prose+card path |
| 4 | **After School** (~7k) | Introduces money strings — verify `localizeMoneyText()` still owns them |
| 5 | **College Support** (~12k) | Highest stakes: admissions outcomes |
| 6 | **Financial Aid** (~39k prose + reports) | Highest stakes and highest volume; do last |

Stage 6 is the only one touching the still-prose-first `src/content/` layer, and it
is the only place the ingest-desync concern is real. Handle it with the same overlay
+ hash mechanism keyed by `(school, topic, subtopic)`; because runtime falls back to
English on hash mismatch, an ingest pass that rewrites a section degrades that
section to English rather than corrupting it.

**Do not flip `PROSE_TRANSLATED` to include `'es'` until stage 6 passes review.**
That list drives `data-prose` on `<html>` and the RTL LTR-pin CSS rule; it means
"the prose is translated", and a partial state must not claim otherwise.

## 6. Concrete first step

Stage 0 only: `localized()`, the extract/reinject scripts, and
`check_translations.mjs`, with **zero translated prose** in the PR. That makes the
architecture reviewable on its own merits before any content decisions ride on it,
and it is the point at which the estimates in §3 get replaced with a measured number
from a real extraction run.
